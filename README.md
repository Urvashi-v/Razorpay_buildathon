# RTO Sentinel

**A cost-calibrated return-risk scorer for Indian COD commerce — that knows what
a false positive costs.**

Most risk models optimise a number nobody pays. This one optimises rupees. RTO
Sentinel scores every incoming order for return-to-origin risk, converts that
score into an expected-value decision using an explicit false-positive cost
model, and returns a graduated, appealable action — never a silent block.

Built for the Razorpay hiring challenge, Track 02 (AI Risk Manager).

---

## ⚠️ Read this first: the data is synthetic

Models in this project are trained on **synthetic data** generated by a sampler
whose parameters are documented in [`config/generator.yaml`](config/generator.yaml)
and anchored to published Indian RTO base rates (see [Sources](#sources)).

**Absolute metric values are therefore not a claim about production
performance.** What synthetic data *can* honestly demonstrate:

- that the pipeline is leak-free;
- that the cost-optimal threshold behaves as the theory predicts;
- that the model beats sensible baselines under identical conditions;
- that the system degrades gracefully.

Overstating this would be the fastest way to lose credibility with a payments
company that has real data. This caveat appears in the API description, in every
evaluation report object, and on the console — not only here.

## Current status: Phase 4 of 6

**Phase 1** established the architecture, **Phase 2** built the data layer,
**Phase 3** built the feature pipeline and the leakage defences, and **Phase 4**
built and measured the baseline ladder. The following are implemented, tested,
and working:

- A reproducible **benchmark generator** with a documented causal simulation
- **PostgreSQL persistence**: 10 tables, Alembic migrations, bulk loader
- **Data validation**: ten check groups, each one verified to actually fire
- **As-of joins** with a brute-force reference implementation and a leakage guard
- **Label maturity**: unresolved orders get a NULL label, never "delivered"
- **Split protocol**: temporal windows inside disjoint customer pools, sealed test set
- **Six feature families** behind a typed dataset contract, each independently
  ablatable, each feature documenting its lookback and its availability at
  scoring time
- **Eleven leakage tests** — the four the specification promises plus the seven
  from Phase 3 — running against real generated data
- **The complete baseline ladder**, rungs 0–4, trained and evaluated on identical
  footing at a cost-derived threshold
- **Experiment tracking**: six versions pinned per result, machine-readable
  records, per-order scores, four plots, and a generated results document
- **Model artefacts**: joblib payload, provenance card, SHA-256 checksum verified
  before unpickling
- A CLI covering generate / validate / migrate / seed / query / features / split /
  train / evaluate
- Typed, validating configuration with a content fingerprint
- FastAPI application with a working `/health` and `/readiness`
- A React console that reads live backend status

**No calibrated model exists yet, so no decision can be produced yet.** Every
Phase 4 rung carries `calibration_method: null`, and the decision engine refuses
an uncalibrated score by design. Calibration, the policy bands and the serving
path are Phase 5. The dashboard and agent layer remain **scaffolded with fixed
interfaces and not implemented**: their endpoints return `501 NOT_IMPLEMENTED`
and their functions raise `NotImplementedError` naming the phase. Nothing returns
placeholder data.

Full breakdown: [ARCHITECTURE.md § Implementation status](ARCHITECTURE.md#8-implementation-status).
Measured results: [docs/ladder_results.md](docs/ladder_results.md).

## Quick start

**Requirements:** Python ≥ 3.11 (developed on 3.12), Node ≥ 20, and optionally
Docker.

```bash
git clone <this-repo> && cd rto-sentinel
```

### Windows (PowerShell)

```powershell
.\scripts\setup.ps1
```

### macOS / Linux

```bash
./scripts/setup.sh
```

Either script creates the virtualenv, installs Python and Node dependencies, and
copies `.env.example` to `.env`. **It never writes a credential** — edit `.env`
and set your own `POSTGRES_PASSWORD` before running against PostgreSQL.

### Verify the install

```bash
rto-sentinel config check
```

That validates every YAML file and prints the configuration fingerprint. It is
the fastest way to confirm the checkout is sound.

### Generate a benchmark dataset

```bash
rto-sentinel generate --seed 42 --customers 4000 --orders 12000 --lenient
```

The same seed and configuration always produce the same data; every dataset
records its seed, generator version, configuration snapshot and creation time.
How the simulator works is documented in full in [docs/simulator.md](docs/simulator.md).

### Load it into PostgreSQL

```bash
docker compose up -d db
```

```bash
./scripts/seed_db.sh --customers 4000 --orders 12000 --lenient
```

That runs migrations, generates, validates, loads, and then queries the row counts
back out. It **refuses to load a dataset that failed validation** — loading
known-bad data is worse than having none, because it looks like a working system.

```bash
rto-sentinel db stats
```

### Train and evaluate the baseline ladder

```bash
rto-sentinel train --seed 7 --customers 20000 --orders 60000
```

That generates the dataset, builds the features, trains all five rungs, evaluates
them on the validation split at the cost-derived threshold, and writes the
comparison table, the machine-readable results, the per-order scores, four plots
and [docs/ladder_results.md](docs/ladder_results.md). Nothing in that document is
written by hand.

The test split stays sealed. `--split test` unseals it and asks for a written
reason; it is meant to be used once, at the end.

### Run the API

```bash
rto-sentinel serve
```

Then in a second terminal:

```bash
cd console && npm run dev
```

The console is at <http://localhost:5173> and the API at <http://localhost:8000>,
with interactive docs at <http://localhost:8000/docs>.

The console will report **"model: not ready"**. That is correct — no model has
been trained yet, and the service says so rather than inventing a probability.

### With Docker

```bash
docker compose up
```

Requires `.env` to exist first; compose refuses to start without
`POSTGRES_PASSWORD` rather than defaulting it to blank.

### The leakage suite

The specification promises four tests a reviewer can run:
`test_no_future_aggregates`, `test_customer_disjoint_splits`,
`test_label_maturity`, `test_target_not_in_features`.

They are in [`tests/leakage/`](tests/leakage/test_leakage_suite.py) and they
**run against real generated data**:

```bash
pytest tests/leakage -v
```

`test_no_future_aggregates` is the interesting one. It rewinds the dataset to a
cutoff — every order still present, but anything not yet resolved has its outcome
and resolution timestamp hidden — recomputes the customer-history feature, and
asserts nothing changed for orders placed before that cutoff. A feature that moves
when the future is removed was reading the future.

The guard is demonstrably capable of failing: `tests/unit/test_asof.py` points it
at a deliberately leaky implementation (an expanding mean over orders *placed*
earlier rather than *resolved* earlier) and asserts it fires.

## What this system does

### 1. Score

A gradient-boosted model returns a **calibrated** probability that this order
becomes an RTO. Sub-100ms, no external calls.

### 2. Decide

An expected-value layer converts probability into an action using the merchant's
own margin and freight numbers:

```
C_fp      = abandonment_on_friction × contribution_margin
S_tp      = intervention_success_rate × rto_cost
threshold = C_fp / (C_fp + S_tp)
```

With the spec's worked example — RTO cost ₹220, contribution margin ₹250,
abandonment 25%, intervention success 60% — the threshold is **0.32, not 0.5**.
And it moves with the merchant's margin: a high-margin brand should flag more
aggressively than a thin-margin reseller. The console exposes all four inputs as
sliders and the threshold recomputes live.

### 3. Act

A four-rung friction ladder:

| Band | Action |
|---|---|
| **LOW** | Nothing. COD offered freely. |
| **ELEVATED** | Prepaid nudge with a small incentive. |
| **HIGH** | COD after one-tap WhatsApp or OTP confirmation. |
| **SEVERE** | Prepaid-only, with a visible appeal path and human review. |

**No rung is a silent hard block.** That is enforced in three separate places —
the policy config validator, the `Decision` type, and the database constraint —
so a future change would have to defeat all three on purpose.

### 4. Explain

Every decision carries deterministic reason codes derived from SHAP
contributions. An LLM renders those into a plain sentence. If it fails, the
console shows the codes and the contribution bars; the decision is unaffected.

### 5. Learn

Outcomes flow back. Overrides are logged as counterfactual evidence. A 2%
randomised control slice of flagged orders receives no friction, because once
friction is applied the true outcome is never observed — and that is the only
clean way to keep measuring precision after the system starts acting.

## The architectural rule

**The ML model outputs a probability. The economic decision engine converts it
into a decision. The LLM is downstream assistance only.**

An LLM should not be scoring risk: it is slow, expensive, uncalibrated and
non-deterministic — four disqualifying properties for a decision that must be
auditable.

So in this codebase the LLM **cannot** generate the probability, choose the
threshold, override the engine, fabricate evidence, modify predictions, or
approve or block an order. Those are not conventions in a document; each is
enforced by a test in
[`tests/architecture/test_layering.py`](tests/architecture/test_layering.py).

## Honest metrics

Reported for every rung of the baseline ladder, on identical footing:

- **PR-AUC** as the primary ranking metric (ROC-AUC is reported but never led
  with — it flatters imbalanced problems)
- **Recall at fixed precision** (80%, 90%)
- **Expected Calibration Error** and Brier score, with a reliability diagram
- **Net ₹ saved per 1,000 orders** — the headline
- **Total ₹ of false-positive cost**, stated separately and never netted away
- **Flag rate**, always, because precision without it is meaningless
- Bootstrap confidence intervals — a point estimate on 5,000 rows is not a result
- A **fairness audit** by pincode tier and order-value band

There is no `accuracy()` function in this codebase. At a one-in-four positive
rate, accuracy rewards doing nothing.

### What the Phase 4 measurement actually showed

Full table and provenance: [docs/ladder_results.md](docs/ladder_results.md).
Three results are worth stating plainly rather than burying:

**Logistic regression beats LightGBM**, on both PR-AUC and net rupees,
reproducibly across seeds. That is not the expected ordering and it was
investigated rather than tuned away. The mechanism: the simulator draws each
order's RTO probability from a **linear combination on the logit scale**, which
makes logistic regression close to the correctly-specified model for this data.
LightGBM at its configured size then pays for flexibility it cannot use — it
scores 0.96 PR-AUC on train against 0.44 on validation. This says something about
the benchmark, not about which model family wins on real RTO data.

**The ceiling is low, and known.** Ranking the validation set by the simulator's
own true probability — the best any model could possibly do — gives PR-AUC 0.598.
The gap between that and rung 3's 0.483 is the honest headroom; the gap between
0.483 and 1.0 is not.

**Rung 2 loses money.** The pincode blocklist nets −₹808 per 1,000 orders: it
flags 4.8% of orders at 26.5% precision, which is barely above the 19.1% base
rate, and the friction costs more than the prevented RTOs save. A baseline that
loses money is a useful result, and it is reported rather than dropped.

## Fairness

A model that concentrates its flags on tier-3 pincodes has not found fraud — it
has found poverty and bad municipal addressing.

So the audit reports flag rate and precision **separately** by tier, and asks
whether precision holds up in the tiers flagged most. If a tier is flagged
materially more often *and* with materially worse precision, the smoothed
geography features get pulled back and the model is retrained. Both the trip and
the remedy go into `REPORT.md` — including the runs where the audit found nothing.

Features this project **refuses to use**, enforced by
[`config/features.yaml`](config/features.yaml) and
[`tests/unit/test_refused_features.py`](tests/unit/test_refused_features.py):

- **Name-derived features of any kind.** Religion, caste and region inference
  from names is a live harm in Indian systems. Names are hashed for identity
  only, never featurised.
- **Raw pincode as a categorical.** With enough trees this becomes a redlining
  machine. Only smoothed, shrunk aggregates with a minimum support threshold.
- **Gender, age, or anything inferable from them.** No lift worth the exposure.
- **Cross-merchant behaviour.** A consent question this project cannot resolve
  responsibly.

## Defense-only

This project is strictly defense-only. It contains no fraud synthesis, no evasion
research, and no offense-capable component. The synthetic generator is a labelled
tabular sampler and is
[named explicitly for scrutiny](ARCHITECTURE.md#7-defense-only-posture).

## Secrets

No API key, password or token is hardcoded anywhere.
`tests/architecture/test_secrets_hygiene.py` sweeps the repository for
key-shaped literals and asserts `.env` is git-ignored.

The only external service is the **Anthropic Claude API**
(`https://api.anthropic.com`), used for the four language jobs. It requires
`ANTHROPIC_API_KEY`. There is no bundled key and no fake response substituted
when it is absent — the agent endpoints return an explicit "unavailable" and the
system continues to score, threshold and act.

The language layer is **off by default**: `RTO_AGENTS_ENABLED` must be true *and*
a key must be present.

## Sources

All market figures are industry estimates from public sources and vary by
category, region and reporting methodology. They anchor the simulator's base
rates and the cost model's bands, and are cited rather than asserted. Full list
with URLs: [docs/sources.md](docs/sources.md).

- **~23%** — India's average e-commerce RTO rate (GoKwik, 180M+ shoppers), versus
  an 8–12% global benchmark
- **26% vs <2%** — RTO on COD versus prepaid orders (Shipway ShipNotes FY25)
- **60–65%** — COD share of Indian e-commerce orders (ET Prime Research)
- **₹150–300** — direct cost of a single RTO
- **₹8,000cr** — estimated annual RTO loss across Indian D2C brands

No proprietary or customer data is used anywhere in this project.
